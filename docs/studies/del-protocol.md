# 决策-证据账本（DEL）：系统设计与 E1–E4 实验协议

**状态：草案 v0.1（2026-11-05），待审批。** 尚未授权、实现或运行。本文不改变 Single 和 Structured Subagents 基线，也不改变 Validation20 及其冻结设置。文中所有付费运行都必须逐次获得授权，并写明规模；未获授权时，入口只输出计划。

## 0. 摘要

- **问题。** 在三个 benchmark 上，Subagents 相对 Single 的差异都在噪声范围内（满分题数 S 36 / T 40 / N 37，共 60 题），耗时却是 Single 的 1.1–2.1 倍。
  - 时间主要耗在串行的关键路径上：leader 委派前单独求解所花的时间，约等于 Single 跑完一整题的一半；之后的等待窗口长度等于最慢 worker 的耗时。
  - 准确率的失败有两种机制：
    - KramaBench / DataClaw：同一先验导致的系统性错误。
    - HDR：网页证据不足。
  - 决策权集中在 leader 手里。worker 真正带来新正确值只有 2 次，两次都被 leader 拒绝。
- **设计。** 不再并行求解过程，改为并行处理不确定性，即分析题的口径分叉和检索题的"候选 × 约束"格。
  - agent 之间交换带出处的类型化对象，不再交换长文报告。
  - 选择和提交由系统规则完成。
  - 所有机制都落在 Claude Code 原生扩展点上（hooks、agent 定义、MCP），提示词只负责解释接口。
- **实验。**
  - Phase 0：实现、离线测试和原生能力探针，零付费调用。
  - Phase 1：在 Validation20 开发集上做 E1 覆盖率、E2 选择和 E3 检索矩阵，用于调试，并给出是否继续的判定。
  - Phase 2：在新抽取的 Holdout40 留出集上做 E4 端到端对照：架构对比纯提示词，并设 Single 噪声底。
- **预算（off-peak 估算，非发票）。**
  - Phase 0：$0。
  - Phase 1：约 $10–18，峰时价约 2 倍。
  - Phase 2：约 $55–67，峰时价约 2 倍。
  - 详见 §4.7。
- **需要你决定的事项**见 §5。

### 1.3 准确率：两种机制

- **KramaBench / DataClaw：共同先验。**
  - 不同条件之间，错误答案两两相同的比例为 81% 和 86%。
  - Krama 上，leader 用自己的 pipeline 算出的第一个答案，其对错与最终答案在 60/60 次运行中完全一致。
  - Krama 上，正确值曾在轨迹中被算出、但没有被提交：S 3 题，T 3 题，N 6 题。覆盖率上升，选择却没有改善。
  - 把三个条件的答案做多数投票，没有收益（15 对 15，17 对 18）。
- **HDR：证据饥饿。**
  - 全程共享 4 次网页请求，约 17% 的请求返回上游 404。错误答案很分散，两两相同的只有 17%。
  - 错误的最终答案出现在搜索结果里的频率，与正确答案一样高（T：错答 6/8，正确 4/4）。可见"在搜索结果中出现"不等于"有证据支持"。
  - 在 7–8 道错题里，正确答案进入网页结果的只有 0–2 次，但有 5–6 次作为假设或 SQL 候选出现过。
  - 最终答案中位约 35 s 时就已出现在 lead 的上下文里，此后还有 91% 的时间。
  - 约束被拆给不同 worker 后，"同时满足全部约束"这一合取关系就丢失了（parallel_104）。
- **决策权。**
  - 120 次 MAS 运行中，worker 带来 lead 之前没见过的正确值只有 2 次（T wildfire-easy-9、N astronomy-hard-12），两次都有工具证据，两次都被拒绝。
  - s2sql 上，N 的 5 道错题中有 2 道，lead 早先已经执行出与金标等价的结果表，后来又改用了别的 SQL。
- **被否定的前提。** 完全重复的观测只占 0–5%。worker 是用不同命令重新熟悉同一批数据，而不是重复同一个调用。因此观测库的价值在于共享和可见，而不是去重。

## 2. 设计原则

1. **并行化不确定性，而不是求解过程。** 求解链本身是串行的。能并行的是显式化之后的分叉和证据格；它们可以用 0 token 的代码执行，配合简短的裁决来处理。
2. **交换类型化、带出处的对象。** 每条主张都必须引用观测 ID，不再传递长文报告。
3. **选择与提交由系统规则完成。** leader 是提议者，不是最终裁决者。
4. **独立性要花在信息来源上，而不是复算上。** framer 看到的视图与 producer 不同；裁决者遵循外部依据层级；必要时使用异构模型。
5. **证据通道是一等资源。** 网页请求必须挂到具体的账本格上，由系统按区分价值分配。
6. **在原生扩展点上强制执行。** hook 负责拒绝与记录，agent 定义负责工具与轮数，MCP 承载账本，代码负责执行与提交。不实现自定义调度器：agent 仍由 CLI 原生启动和调度。

## 3. 系统设计

### 3.1 总体流程

```text
t=0  lead 的首个动作被闸门要求为：启动 framer ×2（各自使用不同视图，看不到 producer 的产物）
     ├─ framer → 账本：Decision 提案（固定类别）/ Constraint 拆分
     └─ producer（即 lead）→ 观测库自动收录 → 交付契约产物：
           分析题：参数化 pipeline.py（DECISIONS + run(d)）
           s2sql：SQL 变体（登记为 Decision）
           检索题：候选生成 SQL + 约束表 → Cell 网格
系统执行器（代码，0 token）：多宇宙 / SQL 变体 / 约束矩阵 → 计算答案敏感度
     └─ 只有"会改变答案"的项进入裁决或取证
裁决者 / 取证者（最小上下文，类型化输出，引用观测 ID）
     └─ 账本更新
提交脚本（确定性，无网络）：答案 = 按规则从账本计算；到截止时间时用默认值提交
```

### 3.2 组件

| 层 | 组件 | 强制方式 | 针对的实测问题 |
|---|---|---|---|
| L0 | **观测库** | PostToolUse hook 把每条工具输出编号为 `obs_id`，记录 agent_id、类别和哈希，写入 `/workspace/.obs/`（含 index.jsonl）；所有 agent 只读 | 正确答案就在 lead 自己的观测里，却没人发现（sql2s_112）；worker 冷启动后重新熟悉数据 |
| L1 | **账本** | MCP 服务（容器内 stdio）做 schema 校验写入，提供 `propose_decision`、`propose_constraint`、`propose_cell`、`attach_evidence`、`claim`、`rule`、`appeal` 和 `view` 工具 | 长文报告；约束被拆散；无法计算覆盖率 |
| L2 | **producer 契约** | Stop hook 校验契约产物可运行、并覆盖账本中所有未关闭的 Decision；不满足时阻止停止（能力待验证，失败时的回退见 §3.5） | 三个 leader 从同一候选集里选出三个不同的值 |
| L2 | **准入闸门** | Agent 的 PreToolUse 规则：brief 必须是结构化头 `item:<id>` 并指向一个未关闭的账本项；worker 类型由项的类型决定，工具由 agent 定义决定，不能凭 brief 去掉工具 | HDR 上 22/46 个仅凭记忆的 worker |
| L2 | **租约** | 某项被 `claim` 后，lead 对同一项的裁决调用，以及对同一网页格的调用，都会被拒绝 | N 的 lead 在窗口期重复做事；多个 agent 抢网页预算 |
| L2 | **网页闸门** | 只在 DEL 臂启用：网页 helper 的调用必须带 `# cell:<id>` 标记，且该格未关闭、预算未用完；共享 helper 本身不改动 | 预算被拆散、抢用；404 浪费 |
| L2 | **提交闸门** | 拒绝任何 agent 直接写入 `submission.json`；最终答案只能由提交脚本写入 | 新的正确值 2/2 被拒绝 |
| L3 | **执行器** | 代码，在同一个无网络容器中以只读数据运行：从默认值出发逐因素（OFAT）变化，敏感项再做成对组合（每题上限 64 个宇宙）；SQL 变体用现有只读 helper 执行并按结果表分等价类；约束矩阵计算存活候选，并给出下一格的预期区分度 | 正确值已算出却没被选中；SQL 漂移；正确答案很早就出现，但之后 91% 的时间都花在区分候选上 |
| L4 | **裁决者** | agent 定义：只能读账本和观测（无 Bash），maxTurns 小，effort high；输入只来自 MCP 的 `view`，由系统抽取原文观测，不包含 producer 的推理；输出为 `rule(id, choice, evidence_ids, basis)`，可以是"不可判别" | 共同先验导致的系统性错误 |
| L4 | **取证者** | agent 定义：只能使用网页 helper（须带 cell 标记）、观测读取和账本写入；只产出 Cell 判定及证据摘录，不提交推荐答案 | 证据饥饿；约束合取丢失 |
| L4 | **提交规则** | 确定性脚本，在 CLI 正常退出后于同一容器内运行，不调用模型：分析题取 `run(裁决结果，否则默认值)`；s2sql 取被选中的变体；检索题取无 unsat 且 sat 证据最多的候选，平局时取 producer 的提议，无解时也回退到 producer 提议并标记；lead 只能凭账本中尚未引用过的新 `obs_id` 申诉一次，由新的裁决者判定 | leader 首答之后还耗费 39–49% 的时间；决策权缺陷 |
| L4 | **截止机制** | SessionStart hook 记录开始时间；到 timeout − 120 s 后，PreToolUse 闸门只放行账本读取，其余调用一律拒绝并提示结束。CLI 超时仍按现行政策记 0 分，各臂一致 | N 的轮询与 sleep；首答之后的长尾 |

**依据层级**（事先固定，与具体任务无关）：
1. 题面原文；
2. 数据文档、codebook 和 KB；
3. 数据本身的原生表示（按存储原样，不插补）；
4. 领域惯例。

裁决必须引用当时可用的最高层级；如果在最高层级上不分胜负，判为"不可判别"，此时采用默认值。

**Decision 的固定类别**（来自 multiverse 文献的通用类别，不是从我们的错题中归纳出来的）：
- 总体范围
- 实体键与去重
- 时间对齐
- 缺失值
- 单位、尺度与符号
- 聚合方式与估计量
- 取整与格式
- 数据源选择

### 3.3 按任务类型实例化

- **KramaBench / DataClaw（分析题）。** 契约产物为 `pipeline.py`，暴露 `DECISIONS`（第一个备选是默认值）和 `run(d)`。最终答案必须能由 `run` 复现。
  - Krama 上，提交脚本生成 `commit_pipeline.py`，以裁决后的 d* 调用 `run`，并按现有 submission 的字段要求写入。现有离线 replay 和打印格式要求不变。
- **HDR s2sql。** 每个 Decision 的备选就是 SQL 变体。执行器比较结果表，只有结果表不同的 Decision 才算敏感。
- **HDR sql2s / parallel（检索题）。**
  - 候选来自 SQL 观测（parallel），或来自登记的主张（sql2s 的网页跳）。
  - 约束是题面中线索的原文片段。
  - 网页请求由约束矩阵按预期区分度排序（即让存活候选减少最多的格），每次请求必须对应一个格。
  - parallel 题的数据库部分与网页部分相互独立，是 HDR 里唯一真正可以并行的结构，可以从 t=0 并行。

### 3.4 时序模型与速度预测

`T_DEL ≈ max(T_producer, T_framer) + T_exec（秒级） + T_adjudicate（一轮并行，约 30–60 s） [+ HDR 的取证轮]`

- producer 不再需要独自权衡口径（这部分推理移给了裁决者），预期 `T_producer ≤ T_Single`。
- 去掉复核型复算之后，委派窗口不再由冷启动的 worker 决定。
- 预测：DataClaw / Krama 上 `T_DEL ≤ 1.15 × T_S`（T 目前在 Krama 上是 386 s，S 是 235 s）；HDR 上 worker 时长相比 T 减少 25% 以上。

### 3.5 实现边界与原生能力

- **代码位置。**
  - 研究条件放在 `scripts/studies/del/`，包括 hooks、MCP 服务、执行器、提交脚本和 agent 定义。
  - 适配器只增加一个显式开启的扩展点，用于额外的 hook 脚本和非空 MCP 配置；必须离线证明在 DEL 关闭时，基线参数逐字节不变。
  - 不改动共享的网页/SQL helper，也不改动基线的 lead 提示。
- **治理。**
  - DEL 引入新角色（framer、裁决者、取证者）和新闸门，这正是 AGENTS.md 所说的"新的分工与协调策略"，只能作为经授权的研究条件存在，不进入基线。
  - lead 专用的指令只放在 lead 提示中，不写入 worker 可见的规则文件（如工作区里的 AGENTS.md / CLAUDE.md）。worker 的说明放在各自的 agent 定义里。
  - MCP 服务只用 Python 标准库实现（stdio JSON-RPC），不新增依赖，也不改动镜像。源码部署只通过 `scripts/server/sync.sh`。
- **调度边界。** agent 一律由 lead 通过原生 Agent 工具启动。"t=0 先启动 framer"通过闸门实现：在 framer 启动之前，拒绝 lead 的其他工具调用。不引入外部驱动或自定义调度器。若你更倾向外部驱动，需要你单独决定，见 §5。
- **已验证**（本仓库或 2.1.286 的生产事件）：
  - PreToolUse `permissionDecision: deny`（Single 策略已在使用）；
  - 父子 agent 的 PreToolUse / PostToolUse 都带 `agent_id`；
  - PostToolUse 带有完整的 `tool_response`；
  - Stop / SubagentStop 带 `background_tasks` 和 `agent_transcript_path`；
  - `--settings` 注入 hooks；
  - agent 定义支持 `effort` 字段。
- **待在 Phase 0 验证**：
  - 在 `--strict-mcp-config` 下使用非空 MCP 配置；
  - `--agents` 定义中的 tools、maxTurns 和 model 字段；
  - Stop hook 能否阻止停止；
  - SubagentStart 的 additionalContext；
  - `fork` 类型能否使用（2.1.286 的 Agent 参数说明提到了它，但这些运行列出的内置类型中没有）。
- **回退方案。** 如果 Stop 阻止不可用，契约检查改在提交脚本中进行：不合规时使用默认 pipeline 的答案，并记为违规。如果 MCP 不可用，账本改用文件实现，由 PreToolUse 校验写入。

### 3.6 对照臂定义

- **S**：严格 Single，现行冻结设置。
- **T**：Structured Subagents，现行冻结的默认基线。
- **DEL**：本文设计，全部机制都强制执行。
- **DEL-P（纯提示词臂）**：lead 指令文本、MCP 工具和 agent 定义都与 DEL 相同，但没有任何闸门、租约或系统提交，由 lead 自己写 submission。用来把 DEL 的收益归因到"强制执行"而不是"指令内容"。
- **DEL-H（可选，暂缓）**：framer 和裁决者改用不同模型族。需要在凭据网关中新增固定路由，并单独授权。

DEL 和 DEL-P 的 lead 指令文本在 Phase 0 起草，经你审批后以 SHA-256 冻结。所有臂使用同样的任务规则和同样的限额文本。

## 4. 实验协议

### 4.1 任务集

- **Validation20 v1（开发集，已反复使用）。** 只用于 Phase 1 的调试和是否继续的判定，任何时候都不作为检验结论报告。

**进入 Phase 2 的门槛**（预注册，三条须同时满足）：
1. **完整性：** DEL 尝试中至少 95% 产生有效提交；因闸门误拒而无法完成的尝试不超过 5%。
2. **速度：** DataClaw 和 Krama 上，DEL 平均耗时不超过 S 的 1.3 倍。
3. **价值信号：** E1 中并集覆盖率比仅 producer 多至少 3 题（以 26 道非平凡题为基数），或 E2 净挽回至少 +2 题且改错不超过 1 题。

若第 3 条不满足：停止，报告边界结论"在这些 benchmark 上，同模型的组织方式无法提高准确率"，并把 DEL-H 作为单独的研究提交审批。

### 4.5 Phase 2：留出集验证（Holdout40，120 题）

- **臂与次数：** S ×3、T ×1、DEL ×3、DEL-P ×1，共 960 次尝试。S 的三次尝试用于给出噪声底。
- **主要终点（预注册）：**
  1. **准确率：** 各 benchmark 的满分题数。DEL 分别对 S、对 T，用首次尝试做精确 McNemar 检验；另报告跨 benchmark 合并的二值计数，两组比较做 Holm 校正。只有当不一致对数超过 S 第 1 次与第 2 次之间的不一致（噪声底）时，才声称有收益。
  2. **时间：** 每次尝试的 CLI 平均耗时，超时计入分母。
  3. **成本：** 已知成本小计及其覆盖率。缺失的计量记为未知，不记为 0。
- **成功标准：**
  - 速度：DataClaw / Krama 上 DEL ≤ 1.15 × S，HDR 上 DEL ≤ 0.8 × T。
  - 准确率：合并后 DEL > S 且 p < 0.05，并高于噪声底；否则如实报告"无准确率收益"。
- **次要指标：**
  - 覆盖率与选择的分解；
  - 闸门事件；无证据准入（DEL 中应为 0）；申诉次数；
  - HDR 上每道正确题消耗的网页请求数；
  - DEL 与 DEL-P 在过程指标上的差异（归因）。
- **统计功效：** 120 题、单次尝试时，大约只能检出净 +10 题以上的效应；更小的效应报告为"不确定"。

### 4.8 风险与有效性威胁

- **同模型天花板：** 错误高度相关，framer 和裁决者也可能共享同一先验。E1、E2 的门槛就是用来判定这一点；未达标时转向 DEL-H。
- **证据与参考答案冲突：** 规则事先固定，冲突题单列报告，不事后调整依据层级。
- **宇宙数量爆炸：** 每题最多 8 个 Decision、64 个宇宙，并只对敏感项继续展开。
- **闸门误拒和机制脆弱：** 由 Phase 1 的完整性门槛约束，误拒情况全部记录。
- **指令混杂：** DEL 使用新的 lead 文本，由 DEL-P 臂控制这一因素。
- **计时偏差：** 各臂交错排程，记录并发数，并标注峰时 / off-peak 价格窗口。
- **开发集反复使用：** Phase 1 结论只用于决定是否继续，不作为检验结论。
